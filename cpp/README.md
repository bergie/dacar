# Dacar C++ implementation

A C++ implementation of [Dacar](../SPEC.md) — a decentralized, offline-first
authorization policy plane for Reticulum networks — targeting
[microReticulum](https://github.com/attermann/microReticulum)-class MCU nodes
(ESP32, nRF52) as well as native platforms. Structured as a PlatformIO library
plus a CMake native build, mirroring microReticulum's layout.

The Python implementation is canonical; this port is validated byte-for-byte
against it (namespace hashes, Ed25519 signatures, transport payloads, state
snapshots, and §13 store records) through Unity test suites driven by
fixtures generated by the Python implementation.

## Build dependencies

### Native (CMake)

- **CMake ≥ 3.15** and a C++17 toolchain (GCC ≥ 9, Clang ≥ 10). GCC 15 is
  supported (the build force-includes `<cstdint>` to paper over libstdc++ 15's
  removal of transitive includes in the pinned dependency revision).
- **Network access on first configure** — dependencies are fetched via
  FetchContent into `cpp/build/_deps/`:
  - [microReticulum](https://github.com/attermann/microReticulum), pinned to
    commit `40fa6288` (override with `-DDACAR_MICRORETICULUM_SOURCE_DIR=/path/to/checkout`
    to use a local checkout)
  - microReticulum itself fetches its shared dependency set:
    [attermann/microStore](https://github.com/attermann/microStore) (Bitcask-style
    persistence + filesystem adapters), [hideakitai/MsgPack](https://github.com/hideakitai/MsgPack)
    (transport serialization), [attermann/Crypto](https://github.com/attermann/Crypto)
    (Ed25519/X25519/SHA-256), and [ArduinoJson](https://arduinojson.org/)
  - [ThrowTheSwitch/Unity](https://github.com/ThrowTheSwitch/Unity) `v2.6.0`
    for the test suites
- No other third-party code — the same dependency stack microReticulum
  firmware already uses.

### Embedded (PlatformIO)

- **PlatformIO CLI** (`pio`), with the platform for your board
  (`espressif32`, `nordicnrf52`, …). Dependencies are declared in
  `platformio.ini` (`lib_deps`) with the same pins as the CMake build; the
  registry-served `microStore` release is pulled by URL to get a current
  revision.
- `USTORE_MAX_VALUE_LEN` is raised to 16384 (Dacar records such as
  `state.msgpack` and `outbox.msgpack` exceed microStore's 1 KB default).
  Keep the value consistent across a fleet: a build with a smaller limit
  drops larger records as corrupt on load.

### Test fixture regeneration (optional)

`FixturesGen.h` is checked in, so running the tests needs no Python. To
regenerate it after changing fixture scenarios:

```sh
python3 -m venv /tmp/dacar-venv
/tmp/dacar-venv/bin/pip install -e ../python   # canonical implementation + deps
/tmp/dacar-venv/bin/python test/tools/generate_fixtures.py
```

## Building and testing

```sh
# from the repository root
make test-cpp          # configure + build + ctest (native Unity suites)

# or manually
cd cpp && cmake -B build -S . && cmake --build build -j && ctest --test-dir build

# embedded runners (on-device)
cd cpp && pio test -e nrf52840-dk-adafruit
```

## Persistence (§13)

`Dacar/Store.h` provides the record model; persistence is delegated to a
`RecordIo` backend:

- **`PosixRecordIo`** (`PosixStore.h`, native): the §13 loose-file layout —
  byte-identical to the Python and JavaScript stores, with the §13.1 file
  modes. A store directory initialized by any implementation is readable and
  writable by the others, including the 64-byte `identity` private-key record.
- **`MicroStoreRecordIo`** (`MicroStoreIo.h`, MCU): the same logical records
  in microStore's `BasicFileStore` (append-only segments + compaction), for
  flash-backed filesystems where loose-file churn is costly. The firmware owns
  the `BasicFileStore` instance and its segment sizing.
- **Provisioning** (`Provisioning.h`, MCU): the `dacar` configuration
  namespace (id 100) exposes salts, anchors, horizon, and topic over
  microReticulum's standard provisioning transport — salts and anchors reach a
  node over BLE/USB/Web-Serial without a filesystem. Salts are `FF_SECRET`
  (never leave the node); trust-affecting fields apply live.

### Storage sizing guide

A CRDT row is ≈ 67 + 16·S bytes on the wire (S = object segments). A
realistic crew deployment (1–3 grants + anchors) stays under 1 KB. On the
nRF52840's 28 KB internal flash filesystem, budget roughly: announce store
(~8–12 KB) + Dacar state + issuer cache, keeping `state.msgpack` growth
bounded through §9 pruning (`prune`). For larger fleets (many issuers,
long-lived tombstones), mount external flash (e.g. RAK15001 FRAM/flash) and
point the store there.

## Layout

- `src/Dacar/` — the library: namespace hashing, HLC, tuples, operations,
  threshold groups, verify-on-ingest, the CRDT, the evaluation engine, the
  delta receive boundary, and the §13 store
- `test/` — Unity suites, one directory per module, driven by byte-exact
  fixtures (`test/fixtures/FixturesGen.h`)
- `test/tools/generate_fixtures.py` — fixture generator (canonical Python)
- `CMakeLists.txt` / `platformio.ini` / `library.json` — native and embedded
  build manifests

See the work documents (rngit) and `../SPEC.md` for the design background.
